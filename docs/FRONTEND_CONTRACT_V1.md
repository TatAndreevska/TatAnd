# Polypak Documentation Portal — Frontend Contract v1

Status: FROZEN BASELINE FOR IMPLEMENTATION
Backend project: Supabase mpqtoeygcoqbzsqczcdu
Source of truth: verified production schema + verified production RPC definitions.

## 1. Core rule
Frontend is a presentation and workflow layer only. It must not reproduce or bypass server-side regulatory, approval, evidence, lifecycle, immutability, snapshot, package or supersession logic.

No frontend field, enum value, status or transition may be invented. If a value is not listed in this contract or returned by production schema, it must not be sent to Supabase.

## 2. Primary MVP workflow
Login -> Role resolution -> Dashboard -> Documentation Requests -> Review -> Product linkage -> Product Version -> Evidence -> Document 1 / Document 2 -> Approval -> Issue -> Package -> Customer access.

## 4. Request lifecycle
Canonical request_status values:
- draft
- submitted
- under_review
- approved
- issued
- closed

Allowed UI transitions:
- draft -> submitted: submit_documentation_request(target_request_id)
- submitted -> under_review: start_request_review(target_request_id)
- under_review -> approved: approve_documentation_request(target_request_id)
- approved -> issued: occurs only through issue_documentation_package(target_package_id)
- draft/submitted/under_review/approved/issued -> closed: close_documentation_request(target_request_id), Polypak only

No other request transition may be generated by frontend.

## 5. Screen contract

### Screen A — Login
Visible fields:
- Email
- Password

Actions:
- Sign in -> Supabase Auth signInWithPassword
- Forgot password -> Supabase Auth password reset flow

After sign-in:
1. Load profiles row for auth.uid().
2. Require profiles.status = active.
3. Load active organization_members for profile_id.
4. Load organization context.
5. Route by member_role.

No custom role name may be created in frontend.

### Screen B — Dashboard
This screen is derived from production records; it creates no lifecycle state.

Customer view:
- Draft requests: documentation_requests.request_status = draft
- Submitted / In review: submitted or under_review
- Approved / Issued: approved or issued
- Recent issued artifacts: issued_artifacts visible through RLS
- CTA: New documentation request

Polypak view:
- Submitted requests awaiting review
- Requests under review
- Documents awaiting approval
- Packages awaiting issue
- Evidence requiring review

Counts are display-only queries. They must not become a second state machine.

### Screen E — Polypak Review queue / Request review
Source: documentation_requests visible through RLS.

Actions:
- Start review -> start_request_review(target_request_id)
  Exact source status required: submitted.
- Link product -> link_request_product(target_request_id, target_product_id)
  Exact source status required: submitted or under_review.
- Approve request -> approve_documentation_request(target_request_id)
  Exact source status required: under_review.
  Backend also requires linked_product_id and at least one approved Product Version.
- Close request -> close_documentation_request(target_request_id)

Frontend must show backend rejection if preconditions are not met; it must not manufacture an approved state locally.

## 7. Production RPC contract
Controlled transitions must use:
- update_draft_documentation_request(target_request_id uuid, patch jsonb)
- submit_documentation_request(target_request_id uuid)
- start_request_review(target_request_id uuid)
- link_request_product(target_request_id uuid, target_product_id uuid)
- approve_documentation_request(target_request_id uuid)
- close_documentation_request(target_request_id uuid)
- approve_product_version(target_product_version_id uuid)
- approve_document(target_document_id uuid)
- issue_document(target_document_id uuid)
- issue_documentation_package(target_package_id uuid)
- supersede_document(target_document_id uuid, replacement_document_id uuid)
- supersede_documentation_package(target_package_id uuid, replacement_package_id uuid)
- set_evidence_review_status(target_evidence_id uuid, target_status evidence_verification_status)
- activate_regulatory_ruleset(target_ruleset_id uuid)

Evidence verified state is not set through set_evidence_review_status(). Verified Evidence must use the server-side evidence verification flow / Edge Function that computes the trusted hash.

## 10. UI restrictions
Frontend must not calculate or assert:
- legal compliance
- PPWR applicability conclusions
- approval eligibility as authoritative state
- Evidence sufficiency
- Evidence validity
- Product Version compatibility
- snapshot contents or hashes
- package validity
- supersession validity
- polypak_regulatory_role
- national compliance/EPR/fee conclusions

The UI may explain backend state and backend validation errors in user-friendly language without changing their legal meaning.

## 11. Error handling
Every mutation must:
- disable the action while pending
- prevent double submission
- show success only after confirmed server response
- display actionable failure state
- re-fetch the authoritative record after success
- never optimistically invent lifecycle status

## 12. Responsive implementation contract
The application is responsive by design, not desktop-only.

Desktop / laptop:
- Primary operational workspace.
- Persistent left navigation.
- Full data tables where useful.
- Multi-column forms where readability permits.

Tablet:
- Collapsible navigation.
- Two-column forms collapse when space becomes constrained.
- Tables may use fewer visible columns and row-detail expansion.
- All approval/review actions remain usable.

Mobile:
- Single-column workflow.
- Navigation becomes drawer/bottom-access pattern as appropriate.
- Request tables become cards/stacked rows; no mandatory horizontal scrolling for core use.
- Forms use full-width controls.
- Primary actions remain clearly reachable.
- File/document viewing and status review remain supported.
- Complex internal Polypak data-heavy screens may be simplified, but no security or lifecycle rule changes by device.

Suggested implementation breakpoints are presentation details, not backend rules. Responsive behavior must be tested at representative mobile, tablet and desktop widths before launch.
